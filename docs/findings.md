## 1. 异常向量表（高置信）

`b1010` 文件偏移 0 起是 8 条 ARM 向量，其中 6 条是 `ldr pc,[pc,#0x18]`
（`E59FF018`），一条 `nop`，一条 `b`：

| 向量 | 指令 | 字面量 | 目标 |
| --- | --- | --- | --- |
| 0 reset | `E59FF018` | `0x9027D524` | 文件 `0x27D524` |
| 1 undef | `E59FF018` | `0x90291C80` | `0x291C80` |
| 2 swi | `E59FF018` | `0x90291D30` | `0x291D30` |
| 3 prefetch | `E59FF018` | `0x90291DA8` | `0x291DA8` |
| 4 data | `E59FF018` | `0x90291DB8` | `0x291DB8` |
| 5 | `E320F000` | 0 | — |
| 6 | `EA00000D` | 0 | — |
| 7 irq | `E59FF018` | `0x90291DEC` | `0x291DEC` |

向量表按 32 字节边界、字面量紧跟其后，是标准的 ARMv7 向量布局。5/6 两条不是
`ldr pc` 也不影响判定。

## 2. 入口矛盾（高置信的观察，中置信的结论）

在基址 `0x90000000` 下，reset 字面量指向文件 `0x27D524`。该处两个 32 位字是：

```
0x27D524: 0x1041D9A8
0x27D528: 0x1041DBA8
```

两者的 ARM 条件码都是 `0x1`（NE），不是 AL；把它们当指令解码会得到带条件的
数据处理指令，不像 reset 入口。`0x27D52C` 才是正常的函数开头：

```
0x27D52C: E3500002  cmp  r0, #2
0x27D530: E3A03000  mov  r3, #0
0x27D534: E92D4070  push {r4, r5, r6, lr}
```

而且文件 `0x25D760` 的启动描述符表**正好引用 `0x9027D52C`**（见 §4）。
因此本原型把初始 PC 设为 `0x9027D52C`，并把“向量表 reset 指到字面量池”
保留为 `fwscan` 的 `WARN`（`vector_reset_points_at_code = false`）。首次实跑
进一步确认了它是**被调用函数**（`push`/`pop`、返回 LR），见 §11。

可能的解释（未验证，按可能性排序）：

1. 向量表在运行时由一级 loader 重定位/补丁，文件里是构建期占位值；
2. 前 8 字节是“入口槽”，loader 在启动时写入真正的分支；
3. 向量表所属的基址与主镜像不同（但 §3 的页表字面量反驳了这一点）。

`-machine entry=0x90000000` 可以回到“从向量表真 reset”的对照组。

## 3. MMU / 页表（高置信）

`mcr p15,0,rX,c1,c0,0`（写 SCTLR）出现在：

```
0x25D728  0x25D938  0x25D99C  0x25D9AC  0x25DA28  0x25DA80  0x129DA50
```

`0x25D7FC` 的字面量是 `0x90020000`，同一段代码里还有 `mcr p15,0,rX,c2,c0,0`
（TTBR0）与 `mcr p15,0,rX,c3,c0,0`（DACR）。结论：

- 主镜像链接/装入基址 **`0x90000000`**；
- 一级页表目标 **`0x90020000`**（基址 + 0x20000）；
- 代码会自己开 MMU；QEMU 不需要替它建页表，但 RAM 必须覆盖页表所在的
  `0x90020000`（默认 128 MiB 足够）。

## 4. 启动描述符表（中置信）

`0x25D758..0x25D800` 是一段紧凑的地址/长度表，前几项：

```
0x25D760  0x9027D52C  0xAE000200   <- 入口或阶段描述符
0x25D768  0x902A2E9C  0x90284000
0x25D770  0x90280000  0x9128DB64
0x25D778  0x10000000  0x00030344
0x25D780  0x912BDEA8  0x10030344
0x25D798  0x9132EC00  0x100A1480  0x0005344C   <- (dest, src, size)?
0x25D7B0  0x9132EBF4  0x100A1094  0x00000004
0x25D7F8  0x1002CB8C  0x90020000               <- (src, dest) 页表?
```

把它读成“从 flash 拷贝若干段到 RAM”的装载表是**推断**：`0x100A1480 + 0x5344C`
仍落在 `a1010` 的 786,432 字节内，`0x1002CB8C` 也是，这与“a1010 映射在
`0x10000000`”自洽。表里也出现了 `0x9132EC00` 这类超出主镜像范围、但在
128 MiB RAM 内的缓冲区地址。

## 5. Flash 窗口（中高置信）

主镜像里落在 `0x10000000..0x10800000` 的 32 位字面量有 **23,660** 个；最小值
`0x10000000`，最大值 `0x107FFF24`。最大值恰好卡在 8 MiB 边界内，因此原型把
flash 窗口定为 **`0x10000000` + 8 MiB**。2026-11-08 起 `a1010` 默认装到
`0x10018000`（`-machine a1010-base=` 可改），让 `bx 0x1002CB8C` 落在 Thumb
序言上；这只是原型默认映射，不代表真实 flash 模块偏移。

`0x100F48C0/0x100F48C4/0x100F48C8` 三项超出了 `a1010` 的大小，说明真实 flash
里还有 `a1010` 之外的内容；原型对未提供部分返回 0，并在文档里标明。
2026-11-08 的运行进一步确认 `0x100F48C0` 被 b1010 init 当作**页表基址**使用，
所以 `mmu-bringup` 会把它回填成 identity 页表地址（§12）。

## 6. 串口候选（中置信）

`0x27D504..0x27D51C` 的字面量池包含：

```
0x80005011  0x88000104  0x80005010  0x80005012  0x80005014  0x8800010A
```

使用它们的指令分布在 `0x27CC08..0x27D304`，全部是字节/半字访问，且在同一段
代码里能看到“取状态 → 判位 → 写数据”的形状。原型因此把 `0x80005000..0x800050FF`
做成字节寄存器串口：`+0x10` 写 TX，`+0x11`/`+0x14` 返回状态（默认 `0x03`），
其余访问记录后返回 0。

这是**假设**，不是数据手册：第一次实跑如果 `d750-uart` 没有输出，`qemu.log`
里的地址/宽度就是下一步要对的协议。

## 7. 指令集与 CPU（中置信）

- 代码同时存在 ARM 与 Thumb-2：`0x54` 是 ARM 异常处理开头
  （`sub lr,lr,#4; push {r3,lr}`），`0x14868` 是 `E92D 4FF7`（`push.w`）。
- 全镜像有 1,623 条 CP15 访问、9,979 条 VFP 形状、17,479 条 NEON 形状的候选
  （后两者会混入数据，只作量级参考）。
- `T-Kernel` 字符串在文件 `0x1264FDA`；`Ver.1.15a` 在 `0x48`。
- ARM 中央处理器 + VFP/NEON + 2014 年 EXPEED 4 世代 → 原型默认 Cortex-A9。
  **没有**从 MIDR 读取值证明型号——主镜像里的 MIDR 读取只是库函数
  （`0x129D230` 等），不是板级识别。换核（例如 A15）必须同时换 private
  block 模型，本原型把 `-cpu` 限制为 `cortex-a9`，避免制造“换个核就能跑”的假象。

## 9. 仍未回答的问题

1. 一级 loader（boot ROM）在 D750 上的真实入口与交付给 `b1010` 的寄存器状态。
2. `0x80005010` 串口的真实寄存器语义（状态位、FIFO、波特率）。
3. ~~GIC/定时器的真实基址~~ —— 2026-11-08 已定为 **`0xE000E000`**（§12）。
4. 双核还是单核；第二个核的启动方式（spin-table / bootreg）。若 a1010 属于
   第二颗核（Cortex-M），两颗核的固件边界需要重新划分。
5. flash 中 `a1010` 之外的内容布局；a1010 本身已确认是 M-profile 镜像，
   不能再当作 A-core 的下一阶段（§12）。
6. `0x1041D9A8/0x1041DBA8` 属于哪个地址空间（`0x10000000` 外设窗口的
   另一段映射？）。

## 11. 首次实跑（2026-11-05）

构建：WSL Ubuntu 26.04 / gcc 15.2 / QEMU 11.1.0。运行：
`tools/run.py` + 上面两个模块。

### 11.1 第一轮：没有低内存、没有辅助

`qemu.log` 的前几条（按发生顺序）：

```
d750-probe: pc=0x9027d534 wr addr=0xfffffff0 size=4 value=0
d750-probe: pc=0x9027d534 wr addr=0xfffffff4 size=4 value=0
d750-probe: pc=0x9027d534 wr addr=0xfffffff8 size=4 value=0
d750-probe: pc=0x9027d534 wr addr=0xfffffffc size=4 value=0
d750-probe: pc=0x9027d53c wr addr=0x00000000 size=4 value=0
d750-probe: pc=0x9027d560 wr addr=0x00000000 size=4 value=0x1041d688
d750-probe: pc=0x9027d584 rd addr=0xfffffff0 ...（四条 pop）
d750-probe: pc=0x00000000 rd addr=0x00000000 ...（跑飞）
```

对应反汇编：

```
0x27D52C  cmp  r0, #2
0x27D530  mov  r3, #0
0x27D534  push {r4, r5, r6, lr}   ; SP=0 -> 0xFFFFFFF0..0xFFFFFFFC
0x27D538  ldrhs r0, [pc, #...]
0x27D53C  str  r0, [r3]           ; 写地址 0
...
0x27D584  pop  {...}              ; LR=0 -> PC=0
```

**结论（高置信）**：

1. `0x9027D52C` 是**被调用函数**，不是 reset 入口；
2. 地址 `0x00000000` 必须是可写 RAM（它写向量槽并读回）；
3. 调用者必须提供 SP 和 LR；否则 `pop` 回 0，PC 跑飞。

### 11.2 第二轮：低内存 + 辅助 SP/LR + halt

机器改动：映射低 64 KiB RAM；`SP=0x97FFFF00`、`LR=0x00000FF0`、`r0=0`；
`0xFF0` 放 4 字节 halt 窗口，取指即请求 QEMU 正常退出。

实测：

```
exit=0  timed_out=False  wall_seconds=0.393  uart=0B  mmio_events=0
d750-halt: pc=0x00000ff0 r0=0x80002000 r1=0x00000000
          sp=0x97ffff00 lr=0x00000ff0
```

**结论**：

- M0 通过：入口执行完并干净返回；
- 返回值 `r0=0x80002000` 形似外设基址，但这一段没有解引用它；
- 这一段**没有任何 MMIO**，所以 M1/M2 还没开始；
- 入口写入 `0x0` 的值 `0x1041D688` 落在 `0x1041xxxx`（flash 窗口外/深处），
  说明真实 flash 布局或地址空间还有未解释的部分（§9 问题 5/6）。

### 11.3 下一步

1. 找 `0x9027D52C` 的调用者：镜像内没有 ARM `BL` 到该地址，只有
   `0x25D760` 的字面量/描述符表；调用者可能在 boot ROM 或 loader。
2. 在 ROM 语义下启动：从描述符表读取入口与段表，模拟“拷贝段 → 调入口 →
   下一阶段”。
3. 用 `-machine entry=` 试其他候选（`0x9025D720` 也返回到了 halt，
   但 `r0=0xEFFD3494`，未见 MMU/MMIO 证据）。
4. 找到真正会访问 `0x8000xxxx` 的路径后再回到 M1/M2。

### 11.4 候选入口扫描（负结果）

对下列地址各跑 2 秒（无 GDB，halt 即退出；`0x9025D700` 用超时）：

| 入口 | 结果 | probe 事件 | UART |
| --- | --- | --- | --- |
| `0x9025D0D4` / `D1C4` / `D360` / `D400` / `D434` / `D464` / `D474` | 返回 halt | 0 | 0 |
| `0x9025D720` | 返回 halt | 0 | 0 |
| `0x90000000`（向量表） | 返回 halt | 0 | 0 |
| `0x9027D52C`（默认） | 返回 halt | 0 | 0 |
| `0x9025D700` | 2 s 未返回 | 0 | 0 |

这些入口覆盖了 `0x25D000..0x25D720` 的函数边界（ARM `E92D` 与 Thumb `B5xx`
混合扫描得到）。全部**没有触达外设**，说明镜像里的早期代码是纯 RAM/CP15 路径；
`0x9025D700` 进入的是等待/轮询循环，但没有 MMIO——很可能在等一个 RAM 标志。

因此“下一阶段”更可能在：

- boot ROM 按 `0x25D760` 表拷贝/跳转之后（ROM 不在本镜像里）；
- 或 `a1010` 之外、本目录没有的 flash 内容（拷贝表引用的
  `0x100A1480 + 0x5344C` 已超出 `a1010` 的 0xC0000）。

这是负结果，但它把“再试哪个函数”的空间基本穷尽了：继续盲试镜像内的函数
不会带来 MMIO，下一步应转向 ROM 交接约定/flash 布局。

### 11.5 结论：需要镜像之外的输入

更新容器只有 `a1010`（786,432 B）、`_wma`、`b1010`。启动到驱动/显示/传感器
所需的那一层大概率在：

1. **boot ROM**（不在更新容器里，通常也不可读）；
2. 或 flash 上 `a1010` 之外的区域（拷贝表引用的 `0x100A1480 + 0x5344C`
   已经越过 `a1010` 的末尾）。

因此当前最值得投入的不是继续写设备模型，而是拿到以下任一：

- 一份完整的 flash/ROM dump（哪怕只读）；
- 或 loader/boot ROM 的交接约定（入口参数、段表语义、下一阶段地址）；
- 或从硬件侧抓到的启动 trace（PC/MMIO 序列）。

没有这些输入时，GUI/CMOS 的寄存器契约只能靠猜，而本项目不猜。

## 12. M1 实跑：启动桩与 a1010 目标（2026-11-08）

完整记录见 [m1-boot-chain.md](m1-boot-chain.md)；这里是结论级摘要。

### 12.1 已证实

- 机器新增 `boot-mode=stub`：从 MMU 垫片 `0x1000` 进 `0x9025D700`，桩逐条
  执行到 `bx ip`，目标 `0x1002CB8C` 以 **Thumb** 进入，现场为
  `LR=0x9025D754`、`r0..r4=0,0,2,0,1`（GDB 实测）。
- 第一条 a1010 MMIO：`wr 0xE000E180 ← 0x00100000`（GIC `ICENABLER0`）。
  据此把 MPCore 基址从 `0x1E000000` 修正为 **`0xE000E000`**；修正后该访问
  被 GIC 模型接住，未建模计数归零。
- b1010 的本地 init 会写 `SCTLR=0x1C05` 打开 MMU，页表基址来自 config 槽
  `0x100F48C0`；只装 a1010 时该槽为 0，init 会把 TTBR0 写成 `0x42` 并在
  `0x9025DA84` 立刻 prefetch abort。机器的 `mmu-bringup` 垫片在 DRAM 顶部
  铺 4 GiB identity 表并回填该槽，固件文件零修改。

### 12.2 新问题：a1010 不是 A-core 的下一阶段

- 继续执行在 `0x100240AC` 撞到 `MRS r0, BASEPRI` / `MSR BASEPRI, r1`；
  这是 **ARMv7-M 专有**指令，Cortex-A9 上必然 undefined（QEMU 已复现）。
- a1010 头部是**大端 Cortex-M 向量表**：`0x00` 初始 MSP=`0x2000F8C0`，
  `0x04` reset=`0x0000C20D`，`0xC20C` 是典型的 `Reset_Handler`（`SystemInit`
  + `.data` 拷贝循环）。字符串为 `D750   Firmware A Copyright Nikon Corp.`。
- 因此 1107 的 `a1010-base=0x10018000` 虽然在 Thumb 解码上自洽，却把
  A-core 的 `bx` 指向了 M-core 固件。两种解释：
  1. 该基址是巧合，A-core 的 `0x1002CB8C` 属于未解出的 A-profile 模块；
  2. D750 有两颗核，a1010 属于 M-core，A-core 的下一阶段尚未拿到。

### 12.3 结论

- **M1 记为“到目标但未闭合”**，不能按完成验收；
- 需要新增输入：整片 flash / 模块偏移表（定位 `0x1002CB8C` 的真正宿主），
  或确认核拓扑的硬件资料；
- 设备侧唯一的新硬结论是 GIC 基址，串口仍是 0 字节。
