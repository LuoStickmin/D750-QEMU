# M1 三条无输入验证（2026-11-09）

> 承接 [m1-boot-chain.md](m1-boot-chain.md)。上一轮结论是“到达 `0x1002CB8C`，
> 但该地址属于 M-profile 固件，M1 不能算闭合”。本轮在不引入任何新固件/硬件
> 数据的前提下，做了三条独立验证，目标是把“`0x1002CB8C` 到底属于谁”从三种
> 猜测收敛。

## 结论先行

| 轨道 | 做了什么 | 关键结果 |
|---|---|---|
| 1. 静态调用链 | 扫 b1010 的 ARM/Thumb BL/BLX、字面量、BSS 回调写入点、描述符表 | b1010 内**没有**调用 `0x9025D700` 的指令/字面量，也**没有**写 `0x902A2EA0/A4/A8` 的代码；描述符表是 4 条 `(dest, src, size)` 拷贝项，源地址全部落在“**b1010 映射在 flash**”的假设内 |
| 2. QEMU 布局枚举 | 12 种 flash 布局 × thumb/ARM 状态 | 只有 **b1010@`0x10000000` + Thumb 位修正** 能跑出连贯的 A-core 路径：veneer → 39 个基本块 → 一次正常的 **SVC**；a1010 的各种基址要么是数据、要么撞 M 指令、要么提前返回 0 |
| 3. M-core 验证 | 用 `mps2-an385`/`cortex-m3` 启动 a1010（BE 向量表转 LE） | a1010 的 `Reset_Handler`/`SystemInit`/`.data` 拷贝全部零异常执行；随后卡在 **`0x00300F40`** 的时钟/PMU 轮询。确认它是 M-core 固件 |

综合：**flash 窗口更像 b1010 的镜像，而不是 a1010**；A-core 启动链缺的是
**一级 boot ROM**（负责安装 `0x90020000` 的向量表、写 BSS 回调、准备页表），
而不是某个设备模型。

## 1. 静态调用链（b1010）

方法：全文件扫 ARM BL/BLX（4 字节对齐）与 Thumb BL/BLX（2 字节对齐），
计算目标并匹配 `0x9025D700..0x9025D75F`；同时搜索相关字面量与 BSS 结构引用。

结果：

- **没有任何指令/字面量指向 `0x9025D700`**。唯一落在桩范围内的直接 BL 是
  `0x9025D6F8 -> 0x9025D720`（桩内部、不是入口）。因此进入桩的调用者不在
  b1010 里。
- **BSS 回调槽没有写入者**。`0x902A2EA0` 只被桩自己的字面量引用；`0x902A2EA4`
  与 `0x902A2EA8` 被 `0x9024809A` / `0x902480B4` 的 runner **读取并尾调用**：
  - `ldr r0,[0x902A2EA4]; ldr r0,[r0]; ... bx r0`
  - 另一分支用 `0x902A2EA8`。
  也就是说 A0/A4/A8 是三个阶段完成回调，**由外部 loader 填**。
- **描述符表是拷贝表**，可解析出 4 条自洽的 `(dest, src, size)`：

  | dest (RAM) | src (flash) | size | 备注 |
  |---|---|---|---|
  | `0x9128DB64` | `0x10000000` | `0x030344` | 从 flash 窗口起点拷贝 |
  | `0x912BDEA8` | `0x10030344` | `0x00F9D2` | |
  | `0x9132EC00` | `0x100A1480` | `0x05344C` | 源范围恰好结束于 `0x100F48CC` |
  | `0x9132EBF4` | `0x100A1094` | `0x000004` | 4 字节补丁 |

  第三条的 `src + size = 0x100F48CC`，而 config 槽 `0x100F48C0/C4/C8` 就在
  这个范围的**最后 12 字节**。这说明 config 槽不是独立 flash 配置区，而是
  **被拷贝 blob 的尾部**。

## 2. QEMU 布局枚举

方法：`boot-mode=stub`，b1010 固定在 `0x90000000`，逐一把候选镜像装到
`0x10000000`（或 `a1010-base`），thumb-fix 开/关各跑一次，记录目标
`0x1002CB8C` 处的字节、后续 PC、异常计数与 MMIO。完整表见
[`evidence/m1/tracks/layout-matrix.md`](../evidence/m1/tracks/layout-matrix.md)。

关键行：

| 布局 | 目标处 | 结果 |
|---|---|---|
| a1010 @ `0x10000000` | `20 00 79 24…`（数据） | undefined 循环 |
| a1010 @ `0x10018000`（当前默认） | `10 b5 14 20…` | 跑到 `0x100240AC` 撞 `MRS/MSR BASEPRI` |
| a1010 @ `0x10018040` | `ae 48 08 60…` | A-profile 可解码，但函数 `pop` LR → 返回 0 |
| a1010 @ `0x10000090` | `48 b1…` | 2 个块后返回 0 |
| **b1010 @ `0x10000000`（Thumb）** | `16 e0`（Thumb `b`） | veneer → `0x2CBBC/0x2CADA/0x2CB26` → `0x3043E/50/64` → `0x14DFF0` → … → **SVC** |

b1010 这一行在 1.5 MiB 镜像下跑了 **39 个唯一基本块、0 prefetch/data abort**，
最后执行到 `0x1002EA64` 后的 `SVC`。SVC 本身是正常的内核调用（T-Kernel），
但 `0x90020000` 的 SVC 向量在镜像里是 Thumb 代码，不是 ARM 向量表，于是
undefined。

用 GDB/镜像补一个最小 ARM SVC 向量（`b` + `movs pc,lr`）后重跑：SVC 正常返回，
继续执行到 **303 个基本块、0 异常**，最终因 `LR=0` 滑到 halt 窗口。说明这条
路径本身是连贯的，缺的是**真实向量表和调用者上下文**。

另外记录到两条来自 flash 代码的未建模读：

```
pc=0x10033aa2  rd addr=0x000f92d4 size=1
pc=0x10093d78  rd addr=0xbd106018 size=1
```

后者形似设备寄存器地址，值得在拿到 loader 后核对。

## 2.1 后续：镜像内 TTBR0 值已验证（同日）

§2 的 b1010-在-flash 路径还留下一个可检验的预测：config 槽 `0x100F48C0` 在
这个布局下读到的是 b1010 文件 `0xF48C0` 的 `0x201E2200`，如果它真是 TTBR0
指针，那么把 identity 页表放到 `0x201E0000`、给机器加一块 `0x20000000` RAM，
MMU init 就应该**不再 fault**。

为此给机器加了四个选项（`tools/run.py` 同名参数）：

| 选项 | 作用 |
|---|---|
| `flash-size=` | flash 窗口大小（默认 8 MiB，最大 64 MiB），用于完整映射 20 MiB b1010 |
| `aux-ram-size=` | 在 `0x20000000` 加一块 RAM（如 `4M`） |
| `mmu-table=` | 把 identity 表放在指定地址，并**不再覆盖** config 槽（用镜像内的值） |
| `vector-fix=on` | 在 payload 的 `0x90020000` 写一个最小 ARM 向量表（SVC 返回、IRQ/FIQ 返回、fault 自旋） |

实验命令：

```sh
qemu-system-arm -M nikon-d750,boot-mode=stub,a1010-base=0x10000000,\
flash-size=0x1400000,aux-ram-size=0x400000,mmu-table=0x201E0000,\
vector-fix=on,thumb-fix=on \
  -cpu cortex-a9 -m 128M -display none -monitor none \
  -serial file:uart.log -D qemu.log -d int,guest_errors,in_asm \
  -no-reboot -nic none -kernel b1010_115a.bin -bios b1010_115a.bin
```

结果（`evidence/m1/tracks/ttbr0-run.log`）：

- 启动日志显示 `table=0x201e0000 (config slot from image)`；
- **prefetch abort = 0**：镜像内的 `0x201E2200` 确实是一个可用的 TTBR0 指针；
- 桩 → veneer → 完整 b1010 flash 路径 → **1 次 SVC，0 undefined，0 abort**；
- 新增三条来自 flash 代码的设备探测：

  ```
  pc=0x10033aa2  rd addr=0x800f92d4 size=1
  pc=0x10093d78  rd addr=0xbd106018 size=1
  pc=0x10066494  rd addr=0x80000004 size=4
  pc=0x100664a0  rd addr=0x80000000 size=4
  ```

  其中 `0x80000000`/`0x80000004` 一度被当作设备基址候选；§2.2 跟进后确认它
  其实是 `{pointer, count}` 工作队列槽。
- 对照实验（同布局、`vector-fix=off`）：SVC 之后立刻进入
  **1,145,766 次 undefined**，说明最小向量表正是继续执行的关键。
- SVC 返回后仍在 `0x1002EA68` 之后的函数尾声处因 `LR=0` 回到 0，随后在低内存
  滑到 halt——这仍是“没有真实调用者栈帧”的限制，不是 MMU 或代码路径的问题。

## 2.2 SVC 返回与 veneer 重定位（同日）

§2.1 之后继续跟了两步：

1. **`0x80000000` 不是设备 ID**，而是一个 `{pointer, count}` 工作队列：
   `0x10066490` 先读 `[+4]` 计数，为 0 时读 `[0]` 指针，再经
   `0x1014DF98`（ARM `ldr pc,[pc,#-4]` veneer → `0x1002EA64` 的
   `swi #0xE8BD`）发起内核调用。`0x80000000` 读出 0 时，`blx r0` 跳到 0，
   这是之前滑到低内存的直接原因之一。
2. **SVC 返回必须恢复 Thumb 位**：第一版 handler 只有 `movs pc,lr`，
   SPSR.T=0，返回后把 `0x1002EA68` 的 Thumb 代码当 ARM 执行。改成
   `mrs r1,spsr; orr r1,#0x20; msr spsr_cxsf,r1; movs pc,lr` 后，
   执行在 Thumb 下继续，经 `0x1014E490` 第二次 veneer 调用到达
   `0x1002F694`。
3. **veneer 表需要重定位**：`0x1014E490` 的 `ldr pc` 目标 `0x1002F694`
   没有 Thumb 位，进入 ARM 后把 Thumb 字节当 ARM 执行 → undefined。
   新增 `veneer-slot=<file offset>`（对 payload 和 flash 镜像同时应用），
   把 `0x14E494` 的字改成 `0x1002F695` 后：

   - **0 undefined、1 次 SVC、0 abort**；
   - 执行继续深入（日志 55 MB、约 130 万条 TB），最终仍在低内存滑到 halt
     （`LR=0`，没有真实调用者栈帧）。

结论：b1010 的 flash 镜像里有**未重定位的 Thumb 指针表**；真实 loader 会按
符号类型给这些槽补 bit0。`0x80000000` 是队列槽，不是外设 ID；在拿到
loader/重定位表之前，继续加“设备”不会推进。

## 2.3 重定位表搜索（同日）

- 在 b1010 里搜索 veneer 槽地址（`0x1014DF9C`、`0x1014E494` 等全地址，以及
  `0x14DF9C`、`0x14E494` 等文件偏移）均无命中：**镜像内没有 veneer 重定位表**。
- veneer 表本身是混合状态：`0x14DF80..0x14DFE8` 里大多数目标已带 Thumb 位
  （奇数），少数是偶数；偶数目标中 `0x1002F114/134/17C`、`0x10000A44`、
  `0x1002EA3C` 按 Thumb 解码都是合法序言，只有 `0x1002EA64` 是真正的
  ARM SWI stub（`swi #0xE8BD`）。说明镜像是**部分重定位**的，loader 的补位
  规则不是简单全表扫描。
- 用 M0 入口 `0x9027D52C` + 完整 b1010 flash 再跑：干净返回 halt，
  `r1=0x80`（原 M0 为 0），说明它现在确实读到了 flash 数据；但它不调用
  `0x9025D700`，loader 的入口仍未定位。

结论：重定位/loader 信息不在 b1010 内；下一步只能靠 flash dump / boot ROM，
或继续从描述符表的拷贝记录反推调用约定。

## 2.4 段布局反推（同日）

从 b1010 的 `0x25D760..0x25D7B8` 读出的 4 条 `(dest, src, size)` 拷贝记录，
链式关系完全自洽：

| 记录 | Flash 源 | 大小 | RAM 目标 | 内容 |
|---|---|---|---|---|
| A | `0x10000000` | `0x030344` | `0x9128DB64` | 开头是 ARM `ldr pc,[pc,#0x18]` 跳转表 |
| B | `0x10030344` | `0x00F9D2` | `0x912BDEA8` | A 的连续续段（Thumb-2 代码） |
| C | `0x100A1480` | `0x05344C` | `0x9132EC00` | 大块数据；镜像目标区为 0 占位 |
| D | `0x100A1094` | `0x000004` | `0x9132EBF4` | Thumb stub `movs r0,#0; bx lr` |

验证：

- A.dest + A.size = B.dest；A.src + A.size = B.src；
- B.src + B.size = `0x1003FD16` —— 正是表项 `0x25D7D0` 存的值；
- C.src + C.size = `0x100F48CC` —— 正好越过 config 槽 `0x100F48C0/C4/C8`；
- C.dest + C.size = `0x9138204C`，超出 20 MiB payload 文件范围；
- D 写在 C 目标前 12 字节，内容是 `00 00 70 47`（`movs r0,#0; bx lr`），
  像一个默认回调。

新增 `loader-copies=on`：在内存 payload 里按这 4 条记录搬运（C 越界时先补零
扩展缓冲）。应用后重跑完整 20 MiB 布局：**路径未变**（没有 PC 进入
`0x91xxxxxx`），说明这些段在当前 b1010 路径上还没被调用；但段表和搬运机制
现在可复现，供后续命中时使用。

结论：loader 的段表就在 b1010 内、结构可读；真正缺的仍是**重定位/调用约定**，
不是段数据本身。

## 2.5 Nikon-Patch IDA 布局（同日）

按提示检查 Nikon-Patch 项目：`simeonpilgrim/nikon-firmware-tools` 的
`IDA_files/D750/D750_Setup_RAM_1.10.idc` / `D750_Setup_RAM_1.02.idc` 给出了
**官方加载布局**（不是 flash dump，但等价于 loader 的装载脚本）：

- ROM 基址是 **`0x90020000`**，不是 `0x90000000`；
- 文件 0 是向量表，reset = **`0x9027D524`**；
- flash `0x10000000` 的内容来自文件内嵌 overlay（1.10 在文件 `0x12BEC08` 起）；
- 另有一段 16 KiB 从文件 `0x280000` 拷到 `0x10500000`。

这意味着我们此前把镜像装在 `0x90000000`，整体错位了 `0x20000`：之前跑的
“桩 `0x9025D700`”其实是 `0x9027D700` 的代码，真正的 `0x9025D700`
（文件 `0x23D700`）是 Thumb 代码。

新增 `payload-base`（`tools/run.py --payload-base`）。用
`payload-base=0x90020000`、真实 reset 入口 `0x9027D52C` 重跑：

- **0 异常**，执行真实 reset 路径（`0x9027D52C → 0x9027D8E0 → …`）；
- 初始化 **`0xA3400000`** 外设块：通道每 `0x1000` 一组，首寄存器 `+0x400`，
  依次写入 `0x40/0x75/0xE3/0x90/0xA7/0xFF/…`；
- 访问 `0xA2000020`、`0xAE000208`、`0xAE000608`；
- 然后**轮询 `0xAE00060C` 8048 次**，因为我们返回 0 而挂住。

结论：Nikon-Patch 项目里没有 flash dump 或 boot ROM，但它的 IDA 脚本给出了
正确的加载布局；下一步是给 `0xAE00060C` 一个“就绪”位，并建模
`0xA3400000` 寄存器块。

## 3. a1010 的 M-core 验证

- 用 `mps2-an385` + `cortex-m3,cfgend=on`，把 a1010 的前 16 个大端向量项
  逐字反转成小端后装入（代码本身是 BE8，指令不变）。
- QEMU 读到 `SP=0x2000F8C0`、`PC=0x0000C20D`，**零异常**执行
  `Reset_Handler → SystemInit → .data 拷贝`。
- 随后卡在 `0x10368..0x103AE` 的时钟/PMU 初始化：轮询 `0x00300F40`（写 `+4`
  和 `+0xC=0xE09A`，等 `0x90000000`/`0xC0000000` 之类的位）。MPS2 没有这个
  寄存器块（该地址落在 SSRAM1，读出恒 0），所以死循环。
- 这独立确认：**a1010 是 D750 的 M-core 固件**，不是 A-core 的下一阶段。
  详细记录见 [`evidence/m1/tracks/mcore-boot.md`](../evidence/m1/tracks/mcore-boot.md)。

## 4. 综合结论

1. **flash 窗口 = b1010 镜像**（至少前 1.5 MiB），这比“a1010 装在
   `0x10018000`”更自洽：
   - 拷贝表的源地址全部落在 b1010 文件范围内；
   - 只有 b1010 布局能跑出连贯的 A-core 代码路径并到达正常 SVC；
   - a1010 已由 M-core 模型独立确认为 Cortex-M 固件。
2. **`0x1002CB8C` 是 b1010 flash 副本里的 Thumb veneer**，`bx` 的 Thumb 位
   修正是必要的；这与 1107 的“Thumb 位”结论一致，但目标模块不是 a1010。
3. **缺的是 boot ROM**，它至少要提供：
   - `0x90020000` 的 ARM 异常向量表（SVC 入口）；
   - BSS 回调 `0x902A2EA0/A4/A8` 的初值；
   - MMU 页表。**已部分验证**：b1010-在-flash 布局下 config 槽读到的
     `0x201E2200` 是一个可用的 TTBR0 指针；把 identity 表放到 `0x201E0000`
     后 MMU init 不再 fault（§2.1），说明页表确实在 `0x20000000` RAM 附近，
     与 M-core 的 SP 同域。
4. **M-core 侧的新地址**：时钟/PMU 块 `0x00300F40`（`+4`、`+0xC`）。这为
   以后单独跑 a1010 提供了第一个要建模的外设。
5. **`0x80000000` 是工作队列槽，不是设备 ID**：结构是
   `{pointer at +0, count at +4}`，代码经 ARM SWI veneer 把它交给内核处理
   （§2.2）。旧的“串口/设备基址”猜测不成立。
6. **veneer 表未重定位**：镜像里 `ldr pc,[pc,#-4]` 的目标是偶数，缺少
   Thumb 位；真实 loader 会按符号类型补 bit0。`veneer-slot` 只修一个槽，
   说明“loader 重定位表”是继续深跑的关键。

## 5. 下一步（仍不需要新固件）

1. **重定位表/loader 约定**（最高优先）：定位 b1010 里的重定位记录，或从
   描述符表反推 loader 如何给 veneer 目标补 Thumb 位；这决定后续所有
   flash 代码调用能否正确互操作。
2. **SVC 接口**：`swi #0xE8BD` 对应 T-Kernel 服务；需要它的入参/返回语义，
   才能让工作队列线程继续而不是返回 0 后滑走。
3. **M-core 继续**：建模 `0x00300F40` 时钟/PMU 寄存器，或打补丁跳过轮询，
   观察 a1010 后续的 UART/传感器访问。
4. **完整 flash/loader**：仍然是最终确认“flash = b1010”、模块偏移与 BSS
   回调初值的最短路径。

## 6. 边界

- 布局枚举用的是**截断镜像**（960 KiB / 1.5 MiB）和**打过补丁的 payload**
  （MMU 关闭、最小 SVC 向量）；这些是诊断手段，不代表真实固件行为。
- §2.1 的 TTBR0 验证使用**完整 b1010 镜像**和 `vector-fix`（最小 ARM 向量表），
  仍不是真实 boot ROM；`0x201E0000` 表是我们铺的 identity 表，不是真机页表内容。
- “flash = b1010”目前是**强证据支持的假设**，仍需要真实 flash dump 或
  loader 确认。
- M-core 结果依赖向量表字节序补丁；代码本身未改（BE8 指令仍为小端）。
