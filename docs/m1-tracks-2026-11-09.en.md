# M1: Three No-Input Checks (2026-11-09)

> Continuation of [m1-boot-chain.en.md](m1-boot-chain.en.md). The previous
> round ended with "the target `0x1002CB8C` executes, but it is M-profile
> firmware, so M1 is not closed". This round runs three independent checks
> without any new firmware or hardware data, to narrow down *whose* code
> `0x1002CB8C` really is.

## Summary

| Track | What was done | Key result |
|---|---|---|
| 1. Static call chain | Scanned b1010's ARM/Thumb BL/BLX, literals, BSS-callback writers, descriptor table | b1010 contains **no** call to `0x9025D700` and **no** code writing `0x902A2EA0/A4/A8`; the descriptor table is four `(dest, src, size)` copies whose sources all fit "**b1010 mapped in flash**" |
| 2. QEMU layout matrix | 12 flash layouts × thumb/ARM state | Only **b1010@`0x10000000` + Thumb-bit fix** produces a coherent A-core path: veneer → 39 basic blocks → a normal **SVC**; a1010 mappings are data, M-instruction crashes, or early returns |
| 3. M-core check | Boot a1010 on `mps2-an385`/`cortex-m3` (BE vectors byte-swapped) | a1010's `Reset_Handler`/`SystemInit`/`.data` copy run with zero exceptions, then hang polling **`0x00300F40`**. Confirms M-core firmware |

Combined: **the flash window looks like b1010's image, not a1010**; what the
A-core chain is missing is the **first-stage boot ROM** (installs the vector
table at `0x90020000`, fills the BSS callbacks, prepares the page table), not a
device model.

## 1. Static call chain (b1010)

Method: sweep every ARM BL/BLX (4-byte aligned) and Thumb BL/BLX (2-byte
aligned), compute targets and match `0x9025D700..0x9025D75F`; also search
related literals and BSS-structure references.

Results:

- **Nothing points at `0x9025D700`.** The only direct BL inside the stub range
  is `0x9025D6F8 -> 0x9025D720` (inside the stub, not the entry). The caller
  that enters the stub is not in b1010.
- **No writer for the BSS callbacks.** `0x902A2EA0` is referenced only by the
  stub's own literal; `0x902A2EA4` and `0x902A2EA8` are **read and
  tail-called** by the runner at `0x9024809A`/`0x902480B4`:
  - `ldr r0,[0x902A2EA4]; ldr r0,[r0]; ... bx r0`
  - the other branch uses `0x902A2EA8`.
  So A0/A4/A8 are three stage-completion callbacks, **filled by an external
  loader**.
- **The descriptor table is a copy table**, with four self-consistent
  `(dest, src, size)` entries:

  | dest (RAM) | src (flash) | size | note |
  |---|---|---|---|
  | `0x9128DB64` | `0x10000000` | `0x030344` | copy from the flash-window start |
  | `0x912BDEA8` | `0x10030344` | `0x00F9D2` | |
  | `0x9132EC00` | `0x100A1480` | `0x05344C` | source range ends exactly at `0x100F48CC` |
  | `0x9132EBF4` | `0x100A1094` | `0x000004` | 4-byte patch |

  The third entry's `src + size = 0x100F48CC`, and the config slots
  `0x100F48C0/C4/C8` are the **last 12 bytes** of that range. So the config
  slots are not a separate flash config area; they are the tail of a copied
  blob.

## 2. QEMU layout matrix

Method: `boot-mode=stub`, b1010 fixed at `0x90000000`, each candidate image
loaded at `0x10000000` (or `a1010-base`), thumb-fix on/off, recording the bytes
at `0x1002CB8C`, the following PCs, exception counts and MMIO. Full table:
[`evidence/m1/tracks/layout-matrix.md`](../evidence/m1/tracks/layout-matrix.md).

Key rows:

| Layout | Target bytes | Result |
|---|---|---|
| a1010 @ `0x10000000` | `20 00 79 24…` (data) | undefined loop |
| a1010 @ `0x10018000` (current default) | `10 b5 14 20…` | reaches `0x100240AC`, hits `MRS/MSR BASEPRI` |
| a1010 @ `0x10018040` | `ae 48 08 60…` | A-profile-decodable, but the function pops LR → returns to 0 |
| a1010 @ `0x10000090` | `48 b1…` | two blocks, then returns to 0 |
| **b1010 @ `0x10000000` (Thumb)** | `16 e0` (Thumb `b`) | veneer → `0x2CBBC/0x2CADA/0x2CB26` → `0x3043E/50/64` → `0x14DFF0` → … → **SVC** |

With a 1.5 MiB image, the b1010 row executes **39 unique basic blocks with zero
prefetch/data aborts**, ending at an `SVC` after `0x1002EA64`. The SVC itself is
a normal kernel call (T-Kernel), but the SVC vector at `0x90020000` is Thumb
code in the image, not an ARM vector table, hence the undefined exception.

After installing a minimal ARM SVC vector (`b` + `movs pc,lr`) via a patched
image, the SVC returns and execution continues: **303 basic blocks, zero
exceptions**, finally sliding to the halt window because `LR=0`. The path
itself is coherent; what is missing is the real vector table and caller
context.

Two unmodelled reads from the flash-resident code were recorded:

```
pc=0x10033aa2  rd addr=0x000f92d4 size=1
pc=0x10093d78  rd addr=0xbd106018 size=1
```

The latter looks like a device register address and should be checked once a
loader is available.

## 2.1 Follow-up: the image's TTBR0 value now verified (same day)

The b1010-in-flash path left one testable prediction: the config slot
`0x100F48C0` reads `0x201E2200` (b1010 file `0xF48C0`) under this layout; if
that really is a TTBR0 pointer, placing the identity table at `0x201E0000` and
adding a `0x20000000` RAM bank should make the MMU init **stop faulting**.

Four machine options were added (also exposed by `tools/run.py`):

| Option | Purpose |
|---|---|
| `flash-size=` | flash window size (default 8 MiB, max 64 MiB) so the full 20 MiB b1010 can be mapped |
| `aux-ram-size=` | add a RAM bank at `0x20000000` (e.g. `4M`) |
| `mmu-table=` | place the identity table at this address and **do not override** the config slot (use the image value) |
| `vector-fix=on` | install a minimal ARM vector table at payload offset `0x20000` (`0x90020000`): SVC returns, IRQ/FIQ return, faults spin |

Command:

```sh
qemu-system-arm -M nikon-d750,boot-mode=stub,a1010-base=0x10000000,\
flash-size=0x1400000,aux-ram-size=0x400000,mmu-table=0x201E0000,\
vector-fix=on,thumb-fix=on \
  -cpu cortex-a9 -m 128M -display none -monitor none \
  -serial file:uart.log -D qemu.log -d int,guest_errors,in_asm \
  -no-reboot -nic none -kernel b1010_115a.bin -bios b1010_115a.bin
```

Result (`evidence/m1/tracks/ttbr0-run.log`):

- the boot log says `table=0x201e0000 (config slot from image)`;
- **prefetch abort = 0**: the image's `0x201E2200` really is a usable TTBR0
  pointer;
- stub → veneer → full b1010 flash path → **1 SVC, 0 undefined, 0 aborts**;
- three new device probes from the flash-resident code:

  ```
  pc=0x10033aa2  rd addr=0x800f92d4 size=1
  pc=0x10093d78  rd addr=0xbd106018 size=1
  pc=0x10066494  rd addr=0x80000004 size=4
  pc=0x100664a0  rd addr=0x80000000 size=4
  ```

  `0x80000000`/`0x80000004` look more like a real device base than the old
  `0x80005000` UART candidate.
- control run (same layout, `vector-fix=off`): immediately after the SVC,
  **1,145,766 undefined exceptions** — the minimal vector table is what lets
  execution continue.
- after the SVC return the function epilogue at `0x1002EA68` still pops `LR=0`
  and returns to 0, then slides through low memory to the halt window. That is
  the "no real caller frame" limit, not an MMU or code-path failure.

## 3. a1010 on an M-profile model

- `mps2-an385` + `cortex-m3,cfgend=on`; the first 16 big-endian vector entries
  of a1010 were byte-swapped to little-endian (the code itself is BE8, so the
  instructions are unchanged).
- QEMU loads `SP=0x2000F8C0`, `PC=0x0000C20D` and executes
  `Reset_Handler → SystemInit → .data copy` with **zero exceptions**.
- It then hangs in the clock/PMU init at `0x10368..0x103AE`, polling
  `0x00300F40` (writes `+4` and `+0xC=0xE09A`, waits for bits such as
  `0xC0000000`). MPS2 does not implement that block (the address lands in
  SSRAM1 and reads 0), so the poll never completes.
- Independent confirmation: **a1010 is the D750's M-core firmware**, not the
  A-core's next stage. Details:
  [`evidence/m1/tracks/mcore-boot.md`](../evidence/m1/tracks/mcore-boot.md).

## 4. Conclusions

1. **The flash window holds b1010's image** (at least the first 1.5 MiB); this
   is more consistent than "a1010 at `0x10018000`":
   - every copy-table source lies inside b1010's file;
   - only the b1010 layout produces a coherent A-core path ending in a normal
     SVC;
   - a1010 has been independently confirmed as Cortex-M firmware on an
     M-profile model.
2. **`0x1002CB8C` is a Thumb veneer in b1010's flash copy**; the Thumb-bit fix
   is required. This agrees with the 1107 Thumb-bit conclusion, but the target
   module is not a1010.
3. **What is missing is the boot ROM**, which must provide:
   - the ARM exception vector table at `0x90020000` (SVC entry);
   - initial values for the BSS callbacks `0x902A2EA0/A4/A8`;
   - the MMU page table. **Partly verified**: under the b1010-in-flash layout
     the config slot reads `0x201E2200`, a usable TTBR0 pointer; placing the
     identity table at `0x201E0000` makes the MMU init stop faulting (§2.1),
     so the page table really lives around `0x20000000` RAM, the same domain as
     the M-core's SP.
4. **New M-core address**: clock/PMU block `0x00300F40` (`+4`, `+0xC`). This is
   the first peripheral to model when bringing up a1010 separately.
5. **New device lead**: 4-byte reads at `0x80000000`/`0x80000004` plus
   `0x800F92D4` and `0xBD106018`; `0x80000000` looks more like the serial/device
   base than the old `0x80005000` candidate.

## 5. Next steps (still no new firmware required)

1. **Complete the vector table / caller context**: the minimal SVC vector works;
   next is to reconstruct the stack frame the epilogue at `0x1002EA68` expects
   (it pops PC=0), or rebuild the boot ROM's calling convention from the
   descriptor table.
2. **Device model**: start with a minimal device at `0x80000000` (4-byte reads
   at `+0`/`+4`) and watch how the probe at `0x10066490` behaves — it may be an
   ID/status register pair.
3. **M-core continuation**: model the `0x00300F40` clock/PMU block, or patch
   out the poll (diagnostic only), and observe a1010's next UART/sensor
   accesses.
4. **Full flash/loader**: still the shortest path to confirm "flash = b1010",
   the module offsets and the BSS callback initial values.

## 6. Boundaries

- The layout matrix used **truncated images** (960 KiB / 1.5 MiB) and a
  **patched payload** (MMU off, minimal SVC vector); these are diagnostic
  tools, not real firmware behaviour.
- The §2.1 TTBR0 check used the **full b1010 image** and `vector-fix` (a minimal
  ARM vector table); it is still not the real boot ROM, and the `0x201E0000`
  table is our identity map, not the real page-table contents.
- "flash = b1010" is a **strongly supported hypothesis**, still needing a real
  flash dump or loader for confirmation.
- The M-core result depends on the vector-table byte-order patch; the code
  itself was not modified (BE8 instructions remain little-endian).
